- **The real "observation failure" bug** the task description references is concretely: `backend/python/app/services/form_filler.py::execute_form_auto_fill`. When `self.browser.observe()` fails or returns no/invalid elements, `observation_error` is set and `needs_human` is forced `True` via `bool(questions) or observation_error is not None` (line ~298) — specifically so a blind run can never look like a clean pass. `backend/python/app/tests/test_form_filler_observation.py` (new, untracked) is the regression test: *"classify_fields cannot distinguish 'no sensitive fields' from 'no observation', so `needs_human` must NOT be derived from it alone."* This is the canonical example of the "observation failure rate" metric in §2 — it already has a well-defined boolean signal (`observation_failed`) sitting in the return payload, unmeasured.

This is the label set §2's LLM metrics should carry.

- **No concurrency cap on browser sessions anywhere.** `backend/python/app/services/browser_automation/session.py` registers sessions in a plain in-memory dict (`_SESSIONS`); `open_session()` calls the selected `BrowserProvider.create()` with no semaphore, no queue, no limit. `BROWSER_PROVIDER` selects `local` (in-process Playwright, dev default) or `browserbase` (remote, real terminate API already implemented — see §4a). Celery's `--concurrency=4` (`Dockerfile.worker`) is today the *only* thing capping how many local Chromium instances can run at once, and only incidentally.

- **No DB connection-pool sizing on the Go side.** `backend/go/internal/database/database.go::NewDB` calls `sql.Open("pgx", dsn)` and never calls `SetMaxOpenConns`/`SetMaxIdleConns`/`SetConnMaxLifetime` — it runs on Go's `database/sql` defaults (unbounded open connections, 2 idle). Python's pools are already deliberately small: `app/services/db.py` (`min_size=1, max_size=4`) and `app/services/privacy_ledger.py` (`min_size=1, max_size=3`). Supabase's own Supavisor pooler (`supabase-local/docker-compose.yml:318`, `supabase/supavisor:2.7.4`) is already part of the stack and unused by the app services, which all connect straight to `db:5432`. See §4e.

- **Celery config** (`app/celery_app.py`): `task_acks_late=True`, `task_reject_on_worker_lost=True`, `worker_prefetch_multiplier=1` (deliberately, per the module's own comment, to stop one worker hogging a batch of long browser/apply tasks), `task_time_limit=900`/`task_soft_time_limit=720`. `Dockerfile.worker` hardcodes `--concurrency=4 -Q tayari` — one queue for everything (browser automation, scraping, learning, delivery). See §4c.

- **`app/main.py`'s Dockerfile CMD ships `--reload` with no `--workers` flag** (`backend/python/Dockerfile`: `CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]`), and `docker-compose.yml` does not override this command for the `prod` profile. `--reload` starts a file-watcher/reloader process and is a development-only flag. See §4b.

- **Existing runbook doctrine** (`docs/Production_Runbook.md`) already names most of the right *signals* to watch during a canary ("HTTP error rate, p95 latency, pod restarts, CPU/memory saturation, queue age, worker failures, candidate cancellation outcomes, and receipt outcomes") and explicitly says *"Do not call a rolling update a canary without a measured traffic split"* and *"Do not force replay browser tasks"* on worker failure. This report's §1 recommendation plugs into that doctrine rather than replacing it — ghost-user runs are the *pre-production* analogue of the canary-window observation the runbook already prescribes for production.

## 1. Shadow / ghost-user testing for an agentic product

### Why the classic pattern doesn't transfer

Traffic-mirroring canary/shadow deployment forks a copy of a real request to a candidate service and *discards* the candidate's response — the request itself is idempotent-ish (an API call, a read) so mirroring it is free. That doesn't work for a browser-automation agent because the "request" *is* the side effect: filling and submitting a real form on a real employer's site. You cannot mirror a real user's live apply-run into a second copy without one of two bad outcomes — a duplicate real submission to the employer, or a second run against a target that has no tolerance for a duplicate (rate limiting, CAPTCHA, a `POST /applications` endpoint that isn't idempotent). Current write-ups on shadow/canary for agentic systems mostly still describe this as a stateless-evaluation problem — forking requests to a candidate and diffing scored outputs — and do **not** address how to avoid double-executing a real-world action; where they do gesture at it, the answer is "dry-run" tool implementations rather than a solved mirroring pattern ([FutureAGI, "LLM Eval with Shadow Traffic and Canary Deployment in 2026"](https://futureagi.com/blog/llm-eval-shadow-traffic-canary-2026/); [AiOps School, "What is shadow deployment?"](https://aiopsschool.com/blog/shadow-deployment/); [DILR.ai, "Voice AI Traffic Ramp: Canary and Shadow Deployment"](https://www.dilr.ai/blog/voice-ai-traffic-ramp-canary-shadow-deployment-enterprise)). Concretely: *"In shadow mode, the agent can call tools, but the tools are 'dry-run' versions that reveal payload issues, schema mismatches, and chaining errors — without producing real effects."* That's the load-bearing idea to borrow, but it means the target the agent talks to during shadow runs cannot be the real employer's site at all — it has to be something built to *look* like one and safely absorb a real submit click.

So "shadow testing" for Tayari has to split into two separate mechanisms that current literature keeps conflating:

1. **Synthetic/ghost-user cohort** — a fake but authenticated user identity that runs the *full* pipeline (resume upload → ATS scoring → job search → browser-fill) end-to-end, on a schedule, against **safe targets**, continuously, in the deployed environment. This is the piece that catches silent regressions (an LLM call falling back to a mock, a form field silently not filled, `needs_human` failing to fire) before a real user hits them.
2. **Pre-production eval harness** — deterministic, repeatable, offline-runnable regression tests against the same safe targets, run in CI. This is not shadow testing in the traffic-mirroring sense at all; it's closer to WebArena/browser-use's own benchmark methodology, and it's the piece that should gate a deploy.

### Safe targets — what to run the browser-fill leg against

Three tiers, in order of fidelity and risk:

**Tier 1 — a self-hosted fake careers-page fixture (build this).** No off-the-shelf open-source fixture that mimics a Greenhouse/Lever/Workday-style application form for agent-testing purposes turned up in research — the closest generic form-testing fixtures (`practice.expandtesting.com`, `testpages.eviltester.com`, the-internet-style Herokuapp clones — see [UltimateQA's "Dummy Automation Websites" list](https://ultimateqa.com/dummy-automation-websites/) and [Expand Testing's practice site](https://practice.expandtesting.com/)) are generic QA-form playgrounds, not ATS-shaped DOM. Recommendation: build a small static/Express fixture app (a handful of HTML pages) that reproduces the actual DOM shapes `FormFiller` has to parse — the `role`/accessible-name pairs `_parse_aria_snapshot`/`_extract_input_roles` in `form_filler.py` already key off (`textbox`, `combobox`, `checkbox`, `radio`, `button`), including the sensitive-field labels `question_queue.classify_fields` is meant to catch ("Are you legally authorized to work?", "Veteran status", "Desired salary"). Serve it from a `docker-compose` service on an internal-only origin so `BROWSER_ALLOWED_ORIGINS` and the origin guard (`agent.py`'s `_guard_credential_entry`/`OriginGuardError`) can be exercised safely, including a scripted "submit" endpoint that records the payload instead of doing anything with it. Cheap, fast, deterministic, runs in CI, and it's the only tier that lets you *inject* the specific failure modes you want regression coverage for (selector rename, added modal, slow-loading field, malformed accessibility tree) on your own schedule.

**Tier 2 — real ATS vendor sandboxes (use these for the periodic ghost-user cohort).** Greenhouse and Lever both ship first-party sandbox environments meant for exactly this:
- Greenhouse: *"Sandboxes work with all Greenhouse APIs, allowing you to test custom integrations, make sample requests, and ensure the payloads are what your development teams expect."* Sandbox API keys are separate from production keys; sandbox users need a distinct email (e.g. `+sandbox` suffix); the sandbox starts as a blank canvas you populate with fictitious job postings and candidates ([Greenhouse Support, "Use a sandbox"](https://support.greenhouse.io/hc/en-us/articles/17053185557787-Use-a-sandbox); [Job Board API docs](https://developers.greenhouse.io/job-board.html)).
- Lever: a sandbox tenant (`hire.sandbox.lever.co`) with its own API credentials, used by partners building integrations; Lever de-dupes candidates by email so repeated ghost-user runs won't pile up duplicate candidate records ([Lever Developer docs](https://hire.sandbox.lever.co/developer/documentation); [Lever API credentials guide](https://lever-old.zendesk.com/hc/en-us/articles/360042364412-Generating-and-using-API-credentials)).
- Workday sandbox tenants exist but are provisioned per customer contract as part of an implementation, not self-serve for a third party wanting to test against a generic Workday-shaped form (Workday's tenant model is Production / Sandbox / Sandbox Preview / Demo-Training, all scoped to a specific customer's Workday instance) — **[unconfirmed]** whether any publicly reachable, unauthenticated Workday demo careers page exists that Tayari could safely target; if not, Workday coverage has to come from the Tier-1 fixture mimicking Workday's known DOM quirks (multi-page wizard flow, iframe-embedded forms), since Workday is architecturally the most different of the three portals ([Workday tenant datasheet](https://www.workday.com/content/dam/web/en-us/documents/datasheets/workday-tenants-datasheet.pdf); [Surety Systems, "Your Guide to Navigating the Workday Sandbox"](https://www.suretysystems.com/insights/your-guide-to-navigating-the-workday-sandbox/)).
- Post a job in each sandbox, point the ghost-user cohort at the public sandbox job-board URL, and let the real `run_browser_agent`/`FormFiller` code path run unmodified — this is the highest-fidelity option because it's the actual vendor DOM, not an approximation, while the submission lands in a sandbox tenant that has zero relationship to a real employer.

**Tier 3 — real production Greenhouse/Lever postings, read-only.** Job *discovery* (search, scrape, ATS-score) can safely run against real live postings continuously (no submit action), which is most of the pipeline anyway. Reserve real-target runs for the non-destructive legs and never let the ghost-user's browser-fill leg reach the submit action on a real posting — gate that explicitly the same way `respect_robots=False` is already gated in `form_filler.py` (a documented, deliberate exception, not a default).

### Eval-harness precedent worth reusing, not reinventing

- **WebArena** is the standard self-hosted benchmark pattern for this exact problem shape: 812 tasks against four self-hosted apps (e-commerce, forum, GitLab-clone, CMS) with a deterministic success function that checks final application/DB state rather than the agent's trajectory ([benchmarkingagents.com, "WebArena: Real Web-Task Agent Benchmark"](https://benchmarkingagents.com/webarena/); [BrowserGym ecosystem paper](https://arxiv.org/pdf/2412.05467)). Tayari's Tier-1 fixture should adopt the same idea: success is checked by asserting on the fixture's recorded-submission payload, not by trusting the agent's own "Completed" summary.
- **browser-use's own eval methodology** ("BU Bench V1": 100 hand-curated hard-but-possible tasks, run repeatedly across models/settings, too-easy and majority-impossible tasks pruned) is open source at [github.com/browser-use/benchmark](https://github.com/browser-use/benchmark) and [github.com/browser-use/eval](https://github.com/browser-use/eval) — directly reusable as the harness shape for a Tayari-specific task set once the Tier-1 fixture exists, since Tayari already depends on `browser-use==0.1.34` ([browser-use benchmark post](https://browser-use.com/posts/ai-browser-agent-benchmark)).
- **The "six failure modes" framing** from FutureAGI's 2026 write-up is a good stratification scheme for what the eval harness should score *separately* rather than aggregate: DOM selector drift, screenshot/visual ambiguity, login-state loss mid-task, modal interruptions, rate-limit/bot-wall cliffs, and irreversibility of the final action. Their stated rationale is directly applicable here — *"per-bucket modal-interruption recovery from 78 percent to 42 percent while aggregate moves from 71 percent to 68 percent is the failure mode teams need [to see]"* — an aggregate success-rate metric would have hidden that regression ([FutureAGI, "Evaluating Browser-Use Agents in 2026: The Six Failure Modes"](https://futureagi.com/blog/evaluating-browser-use-agents-2026/)). Recommend deliberately injecting fault classes into the Tier-1 fixture on a rotation (rename a selector weekly, inject a cookie-banner modal, stub a 429 after N requests, expire the session mid-run) rather than only testing the happy path.
- Playwright's own fixture system (setup/teardown scoped per-test, lazy instantiation) is the right mechanism for standing up the Tier-1 fixture's browser context and seeded fixture data per test run — nothing exotic needed beyond what `playwright==1.49.1` (already a dependency) provides ([Playwright fixtures guide](https://oneuptime.com/blog/post/2026-01-27-playwright-test-fixtures/view)).

### Recommended architecture for Tayari's ghost-user layer

| Layer | What it runs against | Cadence | What it measures | Where results surface |
|---|---|---|---|---|
| **CI eval suite** (deterministic) | Tier-1 self-hosted fixture, seeded + fault-injected | Every PR touching `browser_automation/`, `form_filler.py`, `question_queue.py`, or the optimizer/ATS pipeline | Per-fault-class pass/fail (selector drift, modal interruption, observation-failure handling, origin-guard trip, sensitive-field escalation correctness) | CI job status; a failure blocks merge, matching the existing `py_compile`/pytest gate already required by `backend/python/CLAUDE.md` |
| **Scheduled ghost-user cohort** (continuous, non-blocking) | Tier-2 Greenhouse + Lever sandboxes (real vendor DOM), Tier-1 fixture standing in for Workday, Tier-3 real postings for discovery-only legs | Hourly for the discovery/ATS-score legs (piggybacking on the existing `standing-job-watches-hourly` Celery beat schedule already in `celery_app.py`); every 4-6h for the full apply-through-`needs_human`-boundary leg (deliberately never past submit on Tier 2/3) | Full-pipeline success rate, `observation_failed` rate, `needs_human` rate (should be non-zero and stable — a ghost run that *never* triggers `needs_human` on a sandbox posting seeded with a "Veteran status" field is itself a regression signal), guardrail trip rate, step latency, run duration, LLM cost per run | New Grafana dashboard (§3) fed by the metrics in §2; Sentry breadcrumbs on any unhandled exception in the ghost-user path, tagged distinctly (`run.kind=ghost`) so they never get confused with real-user incidents |
| **Manual/adversarial replay** | Tier-1 fixture with hand-crafted adversarial DOM (nested iframes, shadow DOM, ARIA mislabeling) | Ad hoc, before a browser-automation-touching release | Whatever the specific regression under investigation needs | Local run output / attached to the PR |

A ghost-user identity should be a real row in the `users` table (not a mocked auth context) so it exercises the actual auth/JWT path end to end, tagged (`is_ghost_user=true` or a dedicated email domain) so it's trivially excludable from real user-facing analytics, feedback (`event_log.py`), and the privacy ledger. Route ghost-user browser runs through the existing `run_control.py` lease/cancellation machinery unmodified — that's the same code path production runs use, which is the point.

## 2. Performance and quality metrics that matter for this product

Stage names below are pulled directly from the modules named in the task, not invented. Namespace prefix `tayari_`; Prometheus-style naming (`_seconds`, `_total`, `_bytes` suffixes); every metric keyed so it can be dropped straight into an OTel Metrics SDK meter or `prometheus_client` collector.

| Metric | Type | Labels | Grounding / why this label set | What it catches |
|---|---|---|---|---|
| `tayari_pipeline_stage_duration_seconds` | Histogram | `stage` (`resume_optimize`, `ats_score`, `job_search`, `browser_navigate`, `browser_observe`, `browser_fill`, `browser_agent_step`, `optimizer_guardrails`, `cover_letter_generate`), `outcome` (`success`/`fail`/`needs_human`) | Replaces the stub `stage_complete`/`stage_fail` calls in `app/telemetry/publisher.py` — same `stage_name` vocabulary, now with a real backend and *measured* latency instead of the hardcoded `latency_ms=0` at the one existing call site (`optimizer.py:691-696`) | Stage-level slowdowns; currently invisible because the only wired call site never measures real latency |
| `tayari_llm_call_duration_seconds` | Histogram | `tier` (`fast`/`smart`/`hermes`/`default` — from `llm_service.build_provider(tier)`), `provider` (`provider.active_engine_label()`), `stage` | Per-step agent latency, LLM call included — this is the number that explains why a `browser_agent_step` is slow | LLM provider degradation, tier-routing misconfiguration (e.g. `smart` calls silently resolving to the same cheap model as `fast` because `<VAR>_SMART` was never set) |
| `tayari_llm_tokens_total` | Counter | `tier`, `provider`, `model`, `direction` (`prompt`/`completion`) | Token usage per tier — directly requested; the tier label is the one the repo just added | Cost creep on the `smart` tier (reflexion loop) vs `fast` tier (classification/ranking/drafting) |
| `tayari_llm_cost_usd_total` | Counter | `tier`, `provider`, `model` | Derived from `tayari_llm_tokens_total` × a maintained per-model $/token table | LLM cost per run — Sentry/logs won't show this; it needs to be a first-class counter |
| `tayari_browser_run_outcome_total` | Counter | `portal` (`greenhouse`/`lever`/`workday`/`other`/`unknown` — inferred from `final_url` host pattern), `outcome` (`success`/`failure`/`needs_human`/`cancelled`/`blocked_origin_guard`) | Maps directly onto `AgentResult.success`/`.error` (`agent.py`) and `RunCancelled`/`OriginGuardError` handling already in the run loop | Success/failure/needs-human rate **per ATS portal** — Workday, Greenhouse, and Lever behave very differently and averaging across them hides which one is actually broken |
| `tayari_browser_observation_failure_total` | Counter | `portal` | Directly the `observation_error is not None` boolean already computed in `form_filler.py::execute_form_auto_fill` (currently returned in the payload, never counted anywhere) | The exact bug class already found and fixed — this metric is how you'd have caught it *before* the regression test did |
| `tayari_guardrail_trip_total` | Counter | `guardrail` (`truthfulness`/`keyword_stuffing`/`pii`/`origin_guard`), `verified` (`true`/`false`) | Mirrors `PipelineGate.check()`'s own `verified` field (`gate.py`) plus the origin guard's `OriginGuardError` path (`agent.py`) — the `verified=false` bucket is the important one: it's "we couldn't even check," not "it passed" | Guardrail trip rate, split from "guardrail silently skipped because verification was impossible" — conflating those two is exactly the failure mode `gate.py`'s docstring warns against |
| `tayari_human_escalation_total` | Counter | `field_type` (sensitive field category from `question_queue.classify_fields`), `portal` | `enqueue_questions`/`questions_queued` in `form_filler.py` | Volume and shape of human-in-the-loop load; a sudden drop to zero on a portal that normally escalates sponsorship/veteran-status questions is a silent-regression signal (see Tier-2 ghost-user note in §1) |
| `tayari_form_fill_action_total` | Counter | `portal`, `method` (`profile_value`/`saved_answer`/`simulated`) | `form_filler.py` explicitly distinguishes a real `fill_res.get("success")` action from a `"Simulated fill ..."` fallback string (no `self.browser.page` or no `ref`) | The `simulated` bucket is a leading indicator that the agent is reporting activity it didn't actually perform on the page — currently only visible by reading the `actions` list of a single run |
| `tayari_circuit_breaker_state` | Gauge | `name` (breaker name from `circuit_breaker.py`'s registry) | `CircuitBreaker._state` (`CLOSED`=0/`HALF_OPEN`=1/`OPEN`=2) — currently only logged on transition, never exported | An open circuit breaker on the LLM path degrading silently for minutes before anyone notices the log line |
| `tayari_browser_session_duration_seconds` | Histogram | `provider` (`local`/`browserbase`), `outcome` | `session.py`'s `open_session`/`close_session` lifecycle | Session-provider comparison (local Playwright vs Browserbase-hosted) once/if Browserbase is adopted for prod (§4a) |
| `tayari_browser_concurrent_sessions` | Gauge | `provider` | Size of `session.py`'s `_SESSIONS` dict at scrape time | There is **no cap today** (§0) — this gauge is the prerequisite for setting one; ship the gauge before the cap so you know what "normal" concurrency actually looks like |
| `tayari_browser_session_resource_usage` | Gauge | `provider`, `resource` (`rss_bytes`/`cpu_percent`) | Per-run Chromium child-process resource use, sampled via `psutil` keyed by the session's process (local provider only — remote/Browserbase has no local process to sample) | Memory/CPU per concurrent run — the dominant resource cost of this architecture (§4a) |

Everything above threads a `trace_id`, matching the existing convention in `app/telemetry/publisher.py`, `privacy_ledger.py` (`resource`/`detail` JSONB keyed per action), and `event_log.py` — so a single trace/run ID can join pipeline-stage spans, guardrail results, the privacy ledger, and Sentry error events without inventing a second correlation scheme.

**OTel GenAI semantic conventions caveat:** the natural instinct is to adopt OpenTelemetry's `gen_ai.*` attribute namespace for the LLM-call metrics/spans above. As of mid-2026 that namespace is explicitly **not stable** — the GenAI conventions moved to their own repo (`open-telemetry/semantic-conventions-genai`) and *"no GenAI-specific span, event, metric, or attribute... is marked Stable; the GenAI conventions remain Development"* as of the July 3, 2026 core-spec release ([John Hodge, "The state of the OpenTelemetry GenAI semantic conventions (July 2026)"](https://john-hodge.com/blog/opentelemetry-genai-semantic-conventions/); [dev.to/azena-ai, "OpenTelemetry's GenAI semantic conventions are NOT stable yet"](https://dev.to/azena-ai/opentelemetrys-genai-semantic-conventions-are-not-stable-yet-heres-what-actually-shipped-in-2026-3mke)). Recommendation: keep the `tayari_*` metric names above as the source of truth (they won't get renamed out from under you by an upstream spec churn), and optionally *also* emit `gen_ai.*` span attributes on the tracing side as a bonus for compatibility with off-the-shelf LLM-observability dashboards, understanding that attribute names there may shift before the spec stabilizes.

## 4. CPU / memory / latency optimization playbook

### (a) Headless Chromium/Playwright — the dominant resource cost

**Current state (§0):** `session.py`'s `local` provider launches a fresh in-process Playwright/Chromium browser per run via `browser-use`'s `Agent`, with **zero concurrency cap** anywhere in the code. `Dockerfile.worker`'s `--concurrency=4` on Celery is the only accidental ceiling today, and only for runs dispatched through Celery (not runs served directly by `python-ai`'s SSE `stream_browser_agent` path, which has no cap at all).

**Memory footprint, concretely:**
- A bare Chromium launch allocates roughly **150 MB resident before navigating anywhere**, forking renderer/GPU/network/utility helper processes on top — real-world per-instance footprint commonly lands in the **several-hundred-MB-to-~1GB range once a page is loaded**, and production fleets have hit multi-GB-per-instance leaks when browsers aren't recycled ([datawookie, "Playwright Browser Footprint"](https://datawookie.dev/blog/2025-06-06-playwright-browser-footprint/); [Rendershot, "Headless Chromium at scale: four fixes for a fleet that kept eating RAM"](https://rendershot.io/blog/headless-chromium-fleet-memory)). There's an open Playwright issue (**#38489**) reporting **20 GB+ per instance** with a specific Chromium-for-Testing build under Playwright 1.57 — Tayari pins `playwright==1.49.1`, older than the affected version, but this is worth tracking before any Playwright upgrade ([microsoft/playwright#38489](https://github.com/microsoft/playwright/issues/38489)).
- **Use the `chromium-headless-shell` channel, not full headless Chromium**, for any run that doesn't need pixel-perfect rendering (i.e. every browser-fill run — this product reads the accessibility tree, not pixels). It's a stripped binary built on Chromium's `//content` module with no X11/Wayland/D-Bus dependency and a materially smaller footprint than the full browser Playwright otherwise launches for "headless" mode ([datawookie, Playwright Browser Footprint](https://datawookie.dev/blog/2025-06-06-playwright-browser-footprint/)).
- **Concurrency**: theoretical numbers (15-30 concurrent *contexts* within one shared browser process on an 8-core machine) don't apply here because Tayari launches a separate browser process per run, not shared contexts within one browser. The conservative, production-observed number for separate-process concurrency is **3-4 concurrent browser instances per 8-core host** ([Rendershot](https://rendershot.io/blog/headless-chromium-fleet-memory)). Concrete starting config: **cap concurrent local browser runs at `available_RAM_GB / 1` (i.e. budget ~1 GB per concurrent Chromium instance including headroom for leaks), reviewed empirically starting from 4 on a typical 4-8 vCPU / 8-16 GB worker host**, enforced with an `asyncio.Semaphore` in `session.py::open_session` (currently absent — this is a real gap, not just a tuning knob) or by keeping Celery's browser-task queue concurrency at 4-6 and routing *only* browser-automation tasks through it (see §4c).
- **Offload to Browserbase for production** rather than scaling local Chromium concurrency — the `BrowserbaseProvider` in `session.py` already implements session create/terminate against Browserbase's API, it's just not the default (`BROWSER_PROVIDER` env var defaults to `local`). Current Browserbase pricing (2026): **Free — 3 concurrent browsers / 1 browser-hour; Developer $20/mo — 25 concurrent / 100 browser-hours, $0.12/browser-hour overage; Startup $99/mo — 100 concurrent / 500 browser-hours, $0.10/browser-hour overage; Scale — custom, 250+ concurrent** ([TinyFish, "Browserbase Pricing in 2026"](https://www.tinyfish.ai/blog/browserbase-pricing); [SoftwareSuggest, "Browserbase Pricing 2026"](https://www.softwaresuggest.com/browserbase/pricing)). This decouples browser RAM entirely from the app host and turns a fixed infrastructure-sizing problem into a metered line item — worth it once concurrent ghost-user + real-user browser runs regularly exceed what 4-6 local instances can serve.

### (b) FastAPI async event-loop tuning under concurrent LLM-call-bound load

**Current state (§0):** `backend/python/Dockerfile`'s `CMD` runs `uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload` with **no `--workers` flag**, and `docker-compose.yml` doesn't override it per profile — meaning the `--reload` flag (which spawns a stat-polling reloader process and forces single-process mode) ships in every profile including `prod`. This should never run in production: it's pure overhead (an extra watcher process, no worker parallelism) with zero benefit outside local dev.

Concrete recommendation:
- Split the Dockerfile CMD (or override via `docker-compose.yml`'s `command:` per profile) so `dev` keeps `--reload` and `prod`/`eval` drop it in favor of `--workers`.
- Since this workload is **IO-bound** (awaiting external LLM HTTP calls, not CPU-bound compute), workers should track available CPU cores, not exceed them by much — the commonly cited Gunicorn-derived starting formula is *workers ≈ CPU cores*, adjusted down for I/O-heavy workloads since the event loop itself already handles concurrent awaits within one worker ([Techbuddies, "Top 7 Strategies to Master FastAPI Uvicorn Concurrency & Workers"](https://www.techbuddies.io/2026/03/06/top-7-strategies-to-master-fastapi-uvicorn-concurrency-workers/)). Concrete starting point for a `python-ai` container given, say, 2 vCPU: `uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 2`.
- `uvicorn[standard]==0.34.0` (already the pinned extra in `requirements.txt`) bundles `uvloop` and `httptools` — confirm they're actually selected as the event loop/HTTP parser (uvicorn auto-selects them under the `standard` extra; no extra flag should be needed, but verify with `uvicorn --help` output in the built image rather than assuming).
- Set `--limit-concurrency` to bound in-flight requests explicitly — with LLM calls in the critical path, an unbounded request queue just means more requests waiting on the same upstream rate limit, not more useful throughput.
- Every LLM call in the request path must go through an async HTTP client (`httpx.AsyncClient`, which the codebase already uses in `session.py`'s Browserbase calls) — a synchronous call from an `async def` handler blocks the entire event loop for every concurrent request, not just the one making the call ([jamwithai, "The Concurrency Mistake Hiding in Every FastAPI AI Service"](https://jamwithai.substack.com/p/the-concurrency-mistake-hiding-in)).

### (c) Celery worker concurrency/prefetch for mixed CPU-bound (browser) + IO-bound (LLM) workload

**Current state (§0):** one queue (`tayari`), one worker pool, `--concurrency=4`, `worker_prefetch_multiplier=1` (already correct — the module's own comment explains this is deliberate so one worker doesn't hog a batch of long-running scrape/apply tasks, which matches current guidance that `prefetch_multiplier=1` is right for "real-time"/long-running task mixes ([Celery docs — Concurrency](https://docs.celeryq.dev/en/stable/userguide/concurrency/index.html); [progressstory.com, "production-ready Celery configuration"](https://progressstory.com/tech/python/production-ready-celery-configuration/))).

The gap: **browser-automation tasks (CPU/memory-heavy, each spawning a Chromium process) and pure-LLM tasks (ATS scoring, cover-letter generation — IO-bound, cheap) currently share the same 4 execution slots.** A burst of cheap ATS-scoring requests can starve browser-apply throughput, and vice versa — and worker concurrency for browser tasks is implicitly capped at 4 regardless of how much LLM-only throughput the same host could otherwise sustain.

Concrete recommendation — split into two queues with independently tuned worker pools:
- `tayari-browser` queue: concurrency **4-6** (matches §4a's per-host Chromium budget — this queue's concurrency *is* the browser concurrency cap), `worker_prefetch_multiplier=1` (unchanged — still the right setting for long tasks).
- `tayari-llm` queue: concurrency **16-24** on the same core count, since these tasks spend nearly all their wall time awaiting an external LLM API, not consuming CPU — the commonly cited starting point for IO-bound Celery work on an 8-core host is `--concurrency=32`, and prefetch tuned upward (2-4×) rather than 1, since these are short IO-bound tasks rather than long ones ([Celery School, "Celery Execution Pools"](https://celery.school/celery-worker-pools); [MoldStud, "Celery Configuration Best Practices"](https://moldstud.com/articles/p-celery-configuration-best-practices-enhance-your-task-queue-efficiency)).
- Wire this via `celery_app.conf.task_routes` mapping `app.tasks.automation.*` (browser) to `tayari-browser` and `app.tasks.scraping`/`app.tasks.learning`/`app.tasks.delivery` (LLM/IO) to `tayari-llm`, and run two `celery-worker`-style services in `docker-compose.yml` (or two `-Q` flags on separate `Dockerfile.worker` CMD variants) instead of the current single `-Q tayari`.
- Keep `task_acks_late=True`/`task_reject_on_worker_lost=True` unchanged — that's an at-least-once delivery guarantee unrelated to concurrency tuning, and it's already correct for a task class where losing a submitted-but-unacknowledged apply run is unacceptable.

### (d) Go/Chi gateway

Already fast by construction — chi is *"one of the fastest routers in the Go ecosystem... using a radix tree for route matching"* with zero external dependencies beyond the standard library ([Stack Harbor, "HTTP routing in Go services with chi"](https://stackharbor.com/en/knowledge-base/golang-chi-router-pattern/); [go-chi/chi README](https://github.com/go-chi/chi)). `router.go` already has sensible rate limiters in place (`publicRateLimiter` 10 rps/100 burst, `authRateLimiter` 50 rps/200 burst, `loginRateLimiter` 10 rps/100 burst) and `middleware.Recoverer`. Nothing here needs tuning for throughput; the one real gap on the Go side is entirely on the database-pool side (§4e), not the router.

### (e) Postgres connection pool sizing across Go gateway + Python engine + Celery workers

**Current state (§0):**
- Go (`database.go`): `sql.Open("pgx", dsn)` with **no `SetMaxOpenConns`/`SetMaxIdleConns`/`SetConnMaxLifetime` call** — runs on `database/sql` defaults (unbounded open, `MaxIdleConns` defaults to 2).
- Python main pool (`app/services/db.py`): `asyncpg.create_pool(..., min_size=1, max_size=4)`.
- Python privacy-ledger pool (`privacy_ledger.py`): separate `asyncpg.create_pool(..., min_size=1, max_size=3)`.
- Each Celery worker is a **separate OS process** (prefork pool, `--concurrency=4` today) — if any task-side code lazily creates its own asyncpg/psycopg pool the way `db.py`/`privacy_ledger.py` do, that pool is per-process, so 4 worker processes × whatever `max_size` that code uses is the real connection count, not the single number in the source file.
- Supabase's own **Supavisor pooler** (`supabase/supavisor:2.7.4`) is already deployed as part of `supabase-local/docker-compose.yml` and currently unused by any app service — every service connects straight to `db:5432`.

Standard sizing guidance for the pool that talks directly to Postgres is **`(cpu_cores × 2) + 1`**, kept under Postgres's `max_connections` (default 100), with roughly **75% of that budget reserved for the pooler and 25% for direct/admin connections** ([Aiven docs — PgBouncer connection pooling](https://aiven.io/docs/products/postgresql/concepts/pg-connection-pooling); [swyftstack.com, "PostgreSQL Connection Pool Sizing: Formula + PgBouncer Tuning"](https://swyftstack.com/blog/postgresql-connection-pooling-explained-pgbouncer)).

Concrete recommendation:
1. **Route every app service through Supavisor's transaction-pooling port instead of `db:5432` directly.** It's already running in the stack (`supabase-local/docker-compose.yml:318`) — this is a `DATABASE_URL` host/port change per service, not new infrastructure. Once Supavisor is the single point of contact with Postgres, individual service pool sizes can stay generous without each one needing to reason about the shared `max_connections` budget directly — only Supavisor's own upstream connection count to real Postgres needs to respect `(cores × 2) + 1`.
2. **Explicitly bound the Go pool** — currently the only genuinely unbounded one. Concrete starting values for `database.go::NewDB`: `db.Conn.SetMaxOpenConns(10)`, `db.Conn.SetMaxIdleConns(5)`, `db.Conn.SetConnMaxLifetime(30 * time.Minute)`. Ten is deliberately modest — the Go gateway is a thin auth/routing layer in front of Python for AI work, not a heavy DB consumer, and an explicit bound converts "silent connection exhaustion during a traffic spike" into "requests queue predictably at the pool limit," which is the failure mode you actually want.
3. **Keep Python's existing pools (`max_size=4` / `max_size=3`) but audit for the multiplication problem**: confirm no Celery task path creates its own ad hoc pool per worker process beyond what's already centralized in `db.py`/`privacy_ledger.py`; if `app/services/db.py`'s `get_pool()` singleton pattern is reused (as `event_log.py` already does — `from app.services.db import get_pool`) rather than re-instantiated per task module, 4 worker processes × `max_size=4` = 16 connections tops from that side, well within budget once behind Supavisor.
4. Once behind Supavisor, re-derive Postgres's own `max_connections`/Supavisor's pool size using the `(cores × 2) + 1` formula against the *database host's* actual core count (not the sum of every service's own pool ceiling) — that formula describes Postgres's own parallelism budget, not how generous each client-side pool can be.
