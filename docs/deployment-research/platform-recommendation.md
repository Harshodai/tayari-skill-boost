# Tayari Deployment Platform Recommendation

Research date: 2026-08-13. Fills the gap left by `infra/k8s/README.md` (provider-neutral K8s manifests, no platform, no cost). This doc names a platform, prices it, and states tradeoffs.

**Scale assumption used throughout:** 500 active users, "moderate" agent-run volume = ~50-150 browser-automation runs/day, peak concurrency 3-5 simultaneous headless-Chromium sessions, each run 1-5 min, timeout-capped at 300s (`BROWSER_RUN_TIMEOUT_SECONDS` in `backend/python/app/main.py:803`). Adjust upward if agent-run volume is heavier — this is the one variable that moves every number below.

**A code-level finding that shapes everything in this doc:** the browser-automation endpoints (`/api/v1/browser/automation`, `/api/v1/browser/automation/stream`, `main.py:830-861,1701`) run **inline inside the `python-ai` FastAPI process** via `await run_browser_agent(...)` — not dispatched to Celery. Yet `backend/python/Dockerfile` (the image that builds `python-ai`) never runs `playwright install --with-deps chromium`; only `Dockerfile.worker` (the Celery image, which this code path doesn't use) does. `BROWSER_PROVIDER` defaults to `"local"` (`session.py:132`, `get_provider()`) and isn't listed in `.env.example` at all, nor are `BROWSERBASE_API_KEY`/`BROWSERBASE_PROJECT_ID`. Net effect: **as the repo is currently built, hitting the browser-automation endpoint in any Docker deployment throws a missing-executable error** — there's no working self-hosted path until either the Dockerfile installs Chromium in `python-ai`, or `BROWSER_PROVIDER=browserbase` is set with real credentials. This isn't a hosting-platform problem; it's a pre-existing gap that must close before Section 2's comparison is actionable in production, on any platform. There is also no concurrency limiter on this endpoint — N simultaneous requests spawn N concurrent Chromium instances in one Uvicorn process, bounded only by the 300s timeout, not by a semaphore. Flagging this as unconfirmed-by-me-fixed, not guessed: verified by direct code read, not assumption.

## 1. Ranked platform recommendations

| Rank | Platform | Est. monthly cost | Biggest workload-specific risk |
|---|---|---|---|
| 1 | Single VPS, docker-compose as-is (Hetzner) | **~$160-190/mo** | Single box, single point of failure; no auto-scaling if agent volume spikes |
| 2 | Railway (container PaaS) | **~$230-280/mo** | Per-GB/per-vCPU metered billing directly taxes the Chromium-heavy worker; cost scales with agent-run volume with no cap |
| 3 | Self-managed Kubernetes on Hetzner (k3s, using the existing manifests) | **~$270-320/mo infra + 8-15 eng-hrs/mo** | Operational overhead (etcd/upgrades/CNI) is real and premature at this scale; Hetzner has no managed control plane |

### 1. Single beefy VPS via docker-compose (Hetzner CCX33) — recommended for now

The whole stack is already docker-compose native (`docker-compose.yml`), so this is "ship what you have," not a rewrite.

- **Sizing:** self-hosted Supabase (Postgres+Kong+GoTrue+PostgREST+Realtime+Storage+Studio+Meta) needs ~2-4GB idle; Go gateway ~0.5GB; `python-ai` idle ~1GB (numpy/sklearn/nltk loaded at import); Celery worker sized for 4 concurrent Chromium sessions at a **conservative ~2GB/session** production budget (see Section 2) = 8GB; Redis ~0.5GB; frontend/Caddy negligible. Total: ~14-16GB working set, want 24-32GB for headroom, OS cache, and build layers.
- **Instance:** Hetzner CCX33 (8 dedicated vCPU / 32GB RAM) = €138.49/mo ≈ **$159/mo** at ~1.15 USD/EUR ([Hetzner pricing, June 2026 increase](https://webhosting.today/2026/06/18/hetzners-price-increases-reached-209-the-30-headline-applied-to-a-different-tier/), [exchange rate](https://www.federalreserve.gov/releases/h10/hist/dat00_eu.htm)). Add Hetzner Storage Box or a small object-storage bucket for offsite `pg_dump`/WAL backups (~$5-10/mo) and a snapshot policy (~$8/mo for 10GB+ snapshots, [Fly-equivalent pricing pattern also documented here](https://fly.io/docs/about/pricing/) — Hetzner's own snapshot pricing is comparable). **Total: ~$170-190/mo.**
- Dedicated vCPU (CCX line), not shared (CX line): Chromium is CPU-bound during page render/JS execution, and shared-vCPU noisy-neighbor variance is a real tail-latency risk for a workload already timeout-capped at 300s.
- **What changes vs. today:** almost nothing in the compose file. Concretely: (a) fix the Dockerfile gap above — either move browser-automation to a Celery task so only the already-Chromium-provisioned worker image runs it, or add `playwright install --with-deps chromium` to `backend/python/Dockerfile` too; (b) add an external backup pipeline — self-hosted Supabase's docker-compose ships with **no backup job by default** ([confirmed by community production writeups](https://queryglow.com/blog/supabase-self-hosted)); (c) decide whether to keep the `ollama` service (drop it if using a cloud LLM provider — it's 2-4GB+ of RAM doing nothing if `LLM_PROVIDER` isn't `ollama`); (d) point `CADDY_DOMAIN` at real DNS, which the compose file and `Caddyfile` already support.
- **Biggest risk:** it's one machine. No rolling deploys, no auto-failover, and a bad `docker compose up` restarts everything including Postgres. For 500 users with one on-call engineer this is an acceptable, well-understood tradeoff — not a reason to dismiss it, which is why it ranks #1 despite being the least "cloud-native" option. Mitigate with automated off-box backups (non-negotiable, see Section 3) and a documented rebuild runbook (you already have `docs/Production_Runbook.md` as a starting point, though it's written for the K8s path).

### 2. Railway (container PaaS)

Railway runs arbitrary Docker images (your `Dockerfile`s work unmodified), bills per-second for actual vCPU/RAM consumed: **$20/vCPU/mo, $10/GB RAM/mo**, egress $0.05/GB, volumes $0.15/GB/mo, on top of a $20/mo Pro plan ([Railway pricing docs](https://docs.railway.com/pricing/plans.md)).

- **Policy check:** Railway's Acceptable Use Policy prohibits "bots or scrapers that violate applicable terms of service," not browser automation itself — it's a container platform, so whatever runs in your Docker image runs ([Railway Acceptable Use Policy](https://railway.com/legal/acceptable-use)). No blanket ban on Playwright/Chromium; Railway even publishes a [guide for running Playwright in Docker](https://docs.railway.com/guides/playwright) and hosts community Browserless templates. The real constraint is cost, not policy.
- **Sizing/cost** (each container billed separately): frontend 0.25vCPU/256MB (~$8), go-backend 0.5vCPU/512MB (~$15), python-ai 0.5vCPU/1GB idle (~$20), celery-worker sized for the same 4-concurrent-Chromium budget at 2vCPU/8GB (~$120 — this line item alone rivals the entire VPS option), celery-beat minimal (~$5), redis 0.25vCPU/512MB (~$10). Compute subtotal ≈ **$178/mo** + $20 Pro base + egress (~$5-10) ≈ **$203-208/mo**. Add **Supabase Cloud at $25/mo** (recommended in Section 3 instead of re-deploying the 7-service self-hosted Supabase stack as more Railway containers, which would both cost more and add ops burden) → **~$230-235/mo**, could reach ~$280/mo with backup/observability add-ons.
- **What changes vs. today:** each compose service becomes a separate Railway service (Railway doesn't run `docker-compose.yml` directly — it's one service per repo/Dockerfile, wired with Railway's variable references replacing the compose `environment:` blocks); swap self-hosted Supabase for Supabase Cloud (fewer services to run, see Section 3); use a Railway volume for the Chromium user-data-dir if session persistence across runs is wanted; drop `ollama` (paying $10/GB/mo for an idle local-LLM container is the wrong economics on a metered platform — use OpenRouter, which the code already supports via `OPENROUTER_API_KEY`).
- **Biggest risk:** the Chromium-heavy `celery-worker` container is exactly the kind of workload Railway's per-GB/per-vCPU metering punishes hardest — every concurrent browser session directly and linearly increases the bill, with no reserved-capacity discount. If agent-run volume grows 3x, this line item grows ~3x with it; a VPS's cost is flat until you outgrow the box. Good DX (git-push deploys, zero server ops) buys real convenience, but it's convenience you're paying a ~35-45% premium for at this workload profile, concentrated specifically in the browser-automation container.
- Fly.io is a close alternative to Railway here: also container-native (any Docker image), no Chromium-specific restriction, and separately-priced per-machine RAM (~$5/GB/30 days plus a CPU preset, [Fly.io pricing](https://fly.io/docs/about/pricing/)) — comparable total cost to Railway for this workload, marginally cheaper on RAM-heavy containers, marginally worse on egress outside North America/Europe ($0.04-0.12/GB). Didn't rank it separately because the numbers and tradeoffs land within ~10% of Railway's; pick whichever team already has familiarity with. Render was also verified: its Acceptable Use Policy clause on scraping is scoped to scraping *Render's own service* ("scrape, crawl, or harvest data from **the Service**... without Render's express written consent" — [Render AUP](https://render.com/acceptable-use)), not to customers running Playwright against third-party sites from their own containers — so it isn't disqualified either, but its background-worker tiers ($7/mo for 512MB up to $450/mo for 32GB, [Render pricing 2026](https://checkthat.ai/brands/render/pricing)) price out to roughly the same range as Railway once sized for the same worker.

### 3. Self-managed Kubernetes on Hetzner (k3s), using the existing manifests

This is the "grow into it" option — `infra/k8s/README.md` already describes the target shape; this section prices making it real.

- **Why Hetzner over AWS EKS/GCP GKE at this stage:** Hetzner has **no managed control plane product** at all ([confirmed](https://cloudfleet.ai/blog/cloud-native-how-to/2026-04-hetzner-kubernetes-complete-guide/)) — you self-manage k3s (or pay a third party like Cloudfleet for a managed layer on top of Hetzner nodes). What you get in exchange is real: **Hetzner is ~57% cheaper than AWS EKS for equivalent node capacity** ([eucloudcost.com comparison](https://www.eucloudcost.com/compare/aws-vs-hetzner/)), and dedicated-vCPU Hetzner nodes cost roughly a quarter of comparable AWS/GCP instances.
- **Sizing/cost:** 1x CCX23 (4vCPU/16GB, €85.99 ≈ $99/mo) for frontend+go-backend+python-ai(idle)+redis pods, 1x CCX33 (8vCPU/32GB, €138.49 ≈ $159/mo) dedicated to celery-worker pods (the Chromium-bound workload benefits from not sharing a node with request-serving pods). Infra subtotal ≈ **$258/mo**, + Supabase Cloud $25/mo (do not run Postgres as a StatefulSet on this cluster — see Section 3) ≈ **$283/mo**, + a Hetzner Load Balancer (~$6/mo) and volume/backup storage (~$10-15/mo) ≈ **~$300/mo**. On top of infra dollars: **8-15 engineer-hours/month** of real operational time for a small self-managed cluster (patching, etcd, CNI, upgrades) — [cited estimate](https://cloudfleet.ai/blog/cloud-native-how-to/2026-04-hetzner-kubernetes-complete-guide/), which at even a modest blended cost is worth more than the infra bill itself.
- AWS EKS for the same footprint: $0.10/hr cluster fee (~$73/mo, [AWS EKS pricing](https://www.cloudzero.com/blog/eks-pricing/)) + 2 nodes roughly equivalent to the above (~$400-450/mo on-demand EC2) + NAT gateway (~$32/mo + data processing) + EBS + LB → **$550-700+/mo**. GCP GKE Autopilot: same $0.10/hr cluster fee ([Google Cloud GKE pricing](https://cloud.google.com/kubernetes-engine/pricing)) but pay-per-pod-request billing, which could be *more* cost-efficient than fixed EC2 nodes for a bursty Chromium workload since idle capacity isn't paid for — plausible but **unconfirmed** without a real pod-request profile; ballpark similarly to EKS, likely $400-600/mo. Both give you a real managed control plane (upgrades, HA, IAM integration) that Hetzner doesn't — that's what the extra ~$250-400/mo buys, and it's a legitimate buy once you have a platform team, not yet at 500 users with the stack as-is.
- **What changes vs. today:** this is the one option that uses `infra/k8s/README.md` and `infra/k8s/` largely as designed — the manifests, HPA, PDBs, and the worker-drain script (`scripts/drain-workers.sh`) already assume this target. What's new: pick and wire the Hetzner Cloud Controller Manager + CSI driver, stand up an ingress controller + cert-manager (the doc explicitly leaves this as a "provider-neutral" gap), materialize `tayari-runtime-secrets` per namespace, and resolve the "managed PostgreSQL and Redis are outside the manifest package" line in the doc — that's Section 3's decision, not this cluster's job.
- **Biggest risk:** operational complexity that doesn't pay for itself yet. Nothing about 500 users / one-VPS-worth of traffic needs Kubernetes' horizontal-pod-autoscaling — and the actual bottleneck resource, the Chromium-bound `celery-worker`, doesn't horizontally scale cleanly anyway (each browser run holds a stateful profile/session for its duration; K8s buys you easy *pod* replication, not more concurrent-browser headroom per dollar than the VPS option gets you directly). This is the textbook "Kubernetes before you need it" trap; keep the manifests ready (they already exist) and move to this only when a second engineer or multi-region requirement shows up.

## 2. The Playwright/browser-use hosting decision

### (a) Run Chromium yourself (what the repo does today, once the Dockerfile gap above is fixed)

- **Per-instance memory:** a bare headless Chromium under Playwright peaks around **700MB** in a minimal-page benchmark (706MB headless vs. 1094MB headed, [datawookie.dev browser-footprint benchmark](https://datawookie.dev/blog/2025-06-06-playwright-browser-footprint/)) — that's the floor, not a production number. Real-world production guidance for Playwright-in-Celery-style workers converges on budgeting **~2GB per concurrent worker slot** once you include the Python/Node process, page complexity, DOM/JS execution for real job-application forms, screenshots, and Chromium's well-documented tendency to grow over a long-running worker's lifetime rather than a fresh-process-per-task model ([one 8GB-was-a-lie writeup](https://medium.com/@onurmaciit/8gb-was-a-lie-playwright-in-production-c2bdbe4429d6) reports capping concurrency at 3-4 workers per 8GB for exactly this reason — i.e., ~2GB/slot as the safe planning number).
- **What that implies for this repo specifically:** `Dockerfile.worker`'s CMD hardcodes `--concurrency=4` with **no memory-aware semaphore anywhere in the codebase** (confirmed — no `Semaphore`/`MAX_CONCURRENT` guard in `browser_automation/` or the Celery task layer). At the ~2GB/slot planning number, concurrency=4 needs **~8GB just for the worker**, and that assumes all 4 slots are actually running browser tasks concurrently, which the current code doesn't prevent. Undersizing the container here doesn't degrade gracefully — the Linux OOM-killer takes the process. Practical sizing: either give the worker container 8GB+ (as priced in Section 1), or add an explicit concurrency-aware admission control (a semaphore around session creation) before scaling past the current single-VPS deployment — cheaper to fix in code than to buy around.
- **Concrete recommendation for (a):** keep it, but only after (1) moving the browser-automation call off the request/response path in `python-ai` and onto the already-provisioned Celery worker image (or adding the Chromium install step to both Dockerfiles), and (2) sizing the worker container to ~2GB × max desired concurrency, not the default `--concurrency=4` with no ceiling.

### (b) Switch to Browserbase (already coded, unused)

- **Pricing (2026):** Developer plan **$20/mo** includes 100 browser-hours, overage $0.12/hr; Startup plan **$99/mo** includes 500 browser-hours, overage $0.10/hr ([Browserbase pricing coverage](https://www.tinyfish.ai/blog/browserbase-pricing)). Sessions bill in full-minute increments.
- **At this scale:** 50-150 runs/day × ~3 min average (well under the 300s cap) ≈ 2.5-7.5 browser-hours/day ≈ **75-225 browser-hours/month**. That fits inside the Startup plan's 500 included hours with room to grow, or comfortably inside Developer's 100 hours at the lower end of the volume estimate. **Estimated cost: $20-99/mo**, likely landing on Developer ($20/mo) initially and needing Startup ($99/mo) once volume grows past ~130 hrs/mo.
- **Compared to (a):** at this specific scale, Browserbase is cheaper in raw dollars than provisioning a dedicated 8GB+ worker container ($99/mo vs. the ~$120-160/mo the Chromium-sized worker container costs standalone on Railway or as VPS capacity), and it removes the OOM/sizing risk in (a) entirely — someone else owns Chromium's memory growth. It also already has the provider abstraction wired in `session.py` (`BrowserbaseProvider`), so switching is a config change (`BROWSER_PROVIDER=browserbase` + two env vars), not new code.
- **Recommendation: (b), Browserbase, for production** — it's cheaper at this volume, removes a real operational failure mode (unbounded Chromium concurrency with no admission control, in a container that today doesn't even have the browser binaries installed), and the code path already exists unused. Keep (a)/local Playwright for **local development only**, where the existing `LocalPlaywrightProvider` default is exactly right. This does introduce a new external dependency and a per-run network hop to Browserbase's infrastructure (latency/availability risk) — **unconfirmed:** whether `browser-use==0.1.34` + `playwright==1.49.1`'s CDP client is fully compatible with Browserbase's current remote CDP endpoint version has not been verified here; test this explicitly before cutting over, especially given the pinned-vs-installed Playwright version drift noted below.

### On the Playwright version drift (1.49.1 pinned vs. 1.62.0 locally installed)

This matters for both paths. `browser-use==0.1.34` was built against Playwright's API surface circa 1.49.x; bumping Playwright without re-validating `browser-use` compatibility risks silent breakage (changed CDP protocol handling, launch-arg defaults, etc.) that a passing `pip install` won't catch. Two concrete implications: (1) whichever platform is chosen, **build the Docker image from the pinned `playwright==1.49.1`** — don't let a generic `mcr.microsoft.com/playwright:latest` base image (a common Fly.io/Railway pattern in tutorials) drift ahead of what `requirements.txt` actually pins; (2) if cutting over to Browserbase, verify their remote-CDP endpoint against a 1.49.1 client specifically, not against whatever version their docs examples use (often newer) — this is exactly the kind of thing that passes in a quick manual test and fails under load. Both are pre-migration test items, not blockers to the recommendation above.

## 3. Self-hosted Supabase in production — recommendation: migrate to Supabase Cloud

The repo runs its own Postgres+GoTrue+Kong+PostgREST+Realtime+Storage+Studio stack (`supabase-local/`). Researched whether that's sane at this scale in 2026.

- **Backup/PITR:** self-hosted Supabase's docker-compose ships with **no backup job and no PITR by default** — this is not a configuration oversight to fix later, it's the baseline state ([production writeup, mid-2026](https://queryglow.com/blog/supabase-self-hosted)). Standing up PITR yourself means hand-rolling WAL archiving to S3/B2-compatible storage and rehearsing restores — achievable, but it's infrastructure you're building and maintaining that Supabase Cloud gives you for free ([self-hosted PITR guide confirming this is a DIY WAL-archiving project](https://www.supascale.app/blog/pointintime-recovery-for-selfhosted-supabase-a-complete-guid)).
- **GoTrue patch cadence and real CVEs:** this is not hypothetical risk. In the last ~12 months alone: **CVE-2026-31813**, an OIDC ID-token validation bypass in Supabase Auth allowing authentication bypass, patched in 2.185.0 ([SentinelOne CVE record](https://www.sentinelone.com/vulnerability-database/cve-2026-31813/)); an email-link-poisoning vulnerability via `X-Forwarded-Host`/`X-Forwarded-Proto` header manipulation affecting versions 2.67.1-2.163.0, patched in 2.163.1 ([GHSA-3529-5m8x-rpv3](https://github.com/supabase/auth/security/advisories/GHSA-3529-5m8x-rpv3)); and a user-impersonation permissioning failure patched in 2.5.7 ([GHSA-5hvv-9cqv-894r](https://github.com/supabase/auth/security/advisories/GHSA-5hvv-9cqv-894r)). Production guidance for self-hosted GoTrue explicitly classifies Auth updates as requiring patching **within 24h of a security alert**, because breaking changes ship in the same releases as fixes ([source](https://releasebot.io/updates/supabase)) — meaning someone on the team owns fast-turnaround patch-and-regression-test cycles for an auth server, indefinitely. On Supabase Cloud, this is Supabase's problem the same day it's a CVE; self-hosted, it's a standing on-call responsibility this team doesn't currently appear staffed for (no dedicated platform/security owner named in `docs/Production_Runbook.md`'s gate table beyond generic "Platform/security owner").
- **Cost comparison at 500 users:** Supabase Cloud Pro is **$25/mo base, includes a $10/mo compute credit** that fully covers a Micro instance (1GB RAM) — at 500 MAU, well under the 50,000-MAU free-tier auth threshold, **actual cost is likely exactly $25/mo** ([Supabase 2026 pricing breakdown](https://makerkit.dev/blog/saas/supabase-pricing)). That's cheaper than the engineering time saved by not running WAL archiving and 24h-SLA auth patching, before even counting infra dollars for the self-hosted Postgres/GoTrue/Kong/Realtime/Storage containers themselves (a non-trivial RAM line item in every Section 1 cost estimate above).
- **Recommendation: migrate to Supabase Cloud.** Self-hosting Supabase made sense as the local-dev/self-hostable-product default this repo was built around, and `VITE_USE_SELF_HOSTED`/`USE_SUPABASE` already exist as the toggle points — but "self-hostable as a product feature for end users who run their own instance" and "how *we* run our own production deployment" are different questions, and this doc is answering the second one. Keep local self-hosted Supabase for development and for the product's own self-host story (that's a feature, not a mistake); run the team's actual production instance on Supabase Cloud. If data residency or a hard compliance requirement rules out Supabase Cloud later, the fallback isn't "self-host the whole Supabase stack" — it's a plain managed Postgres (DigitalOcean Managed Postgres from **$15.15/mo**, no IOPS fees, [DigitalOcean pricing](https://selfhost.dev/blog/managed-postgresql-comparison-2026/)) plus a lighter auth layer (Supabase Auth itself, self-hosted alone rather than the full 7-service stack, is a smaller surface than Kong+Realtime+Storage+Studio all together) — but that's a "only if forced" branch, not the default recommendation.

## 4. Concrete next steps

Ordered for the Section 1 #1 recommendation (VPS) with the Section 2/3 decisions folded in — an engineer can start executing without further research:

1. **Fix the browser-automation Dockerfile gap first, independent of platform.** Either add `RUN python -m playwright install --with-deps chromium` to `backend/python/Dockerfile` (matching `Dockerfile.worker`), or move the `/api/v1/browser/automation` handler to dispatch a Celery task instead of calling `run_browser_agent` inline in `main.py:840`. Do this before any platform migration — it's broken today on every platform.
2. **Decide Browserbase vs. self-run Chromium (Section 2) and act on it.** If Browserbase: sign up, set `BROWSER_PROVIDER=browserbase`, `BROWSERBASE_API_KEY`, `BROWSERBASE_PROJECT_ID` (add these to `.env.example` — currently undocumented), and run a load test at expected concurrency against the pinned `playwright==1.49.1` client before cutover. If self-run: add an explicit concurrency semaphore around browser-session creation and size the worker container to ~2GB × max concurrency.
3. **Migrate production auth/DB to Supabase Cloud (Section 3).** Create a Supabase Cloud project, run the existing `backend/db/migrations/` against it, point `VITE_SUPABASE_URL`/`SUPABASE_URL`/keys at the cloud project, and decommission the `supabase-local/` stack for the production deployment only (keep it for local dev, unchanged).
4. **Provision the Hetzner CCX33 VPS**, install Docker + Compose, clone the repo, `cp .env.example .env` and fill in real secrets (`JWT_SECRET` must now match Supabase Cloud's, not a local `supabase-local/.env`), drop the `ollama` service from the compose profile unless actually using a local LLM.
5. **Set up automated offsite backups before going live** — this has no default in the repo today. `pg_dump`/WAL-archive schedule to a Hetzner Storage Box or S3-compatible bucket, plus a quarterly rehearsed-restore calendar reminder (not just a cron job nobody watches).
6. **Point DNS at the box, set `CADDY_DOMAIN`**, bring the stack up with `docker compose --profile prod up -d --build`, run `curl <host>/api/health` and `curl <host>:8002/health` per `CLAUDE.md`'s health-check convention.
7. **Run the existing staging/production gates** in `docs/Production_Runbook.md`'s preflight table before flipping real traffic — that runbook was written for the K8s path but its gate list (image integrity, secrets, backups, product gate, billing gate) applies unchanged to the VPS path; only the `scripts/deploy-environment.sh` mechanics differ.
8. **Re-evaluate Section 1's #2/#3 options only when a concrete trigger shows up** — sustained agent-run volume 3-5x the assumption above (revisit Railway/Fly for elastic burst capacity), or a second engineer joining ops (revisit the Hetzner K8s path, manifests are already sitting in `infra/k8s/` ready to use).
