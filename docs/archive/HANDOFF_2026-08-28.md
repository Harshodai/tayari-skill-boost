## 4. Everything tried and failed (with the actual results)

This is the part worth reading closest — several of these looked like real bugs and weren't, and one
looked like a coordinate-tooling problem and was actually a real, serious bug.

### 4.1 "SavedSearches save button does nothing" — investigated wrong 3 times before the 4th worked
- **Attempt 1** (previous session): read the code, concluded it looked correct, blamed browser-session
  flakiness from repeatedly switching auth modes mid-session. **Result: wrong conclusion, bug was real.**
- **Attempt 2** (this session, early): re-tested in a supposedly-clean tab, still failed, hypothesized a
  screenshot-vs-real-viewport coordinate scaling mismatch (screenshots render at 800px wide, real
  viewport was 1280px) after noticing a `ref`-resolved click landed at very different pixel coordinates
  than my screenshot-based guess. **Result: a real, separate tooling gotcha (worth knowing for future
  browser-automation work in this environment), but not the actual bug** — a `ref`-based click (which
  auto-resolves real coordinates) still produced nothing.
- **Attempt 3**: hypothesized Kong/PostgREST auth-header quirks, HMR artifacts, stale dev-server
  processes. Spent real time on each; all ruled out with direct evidence (`ps aux`, `curl` against Kong
  directly, fresh-tab reproduction).
- **Attempt 4 (worked)**: added a temporary `console.log` directly inside the mutation function and
  inside the `useAuth()` destructure, drove a full clean reload, and got the real answer in one shot:
  `user` alternates **null → real object → null** on every page load, settling on `null` by the time
  any button is clicked. Traced the reset to `AuthContext.tsx`'s `auth:unauthorized` listener, fired by
  `src/api/client.ts`'s `handleUnauthorized()` on literally any Go-gateway 401 — which this session's
  test setup produces constantly via background polls (`GET /api/v1/agent/runs/active`, etc.) because
  the frontend was in Supabase-auth mode while the Go gateway was in self-hosted-JWT mode. **Result:
  the actual root cause, fixed in `e1f1c93`.**
- **Lesson**: instrumenting the exact value at the exact call site beats re-reading code you've already
  read twice. Should have done this on attempt 1, not attempt 4.

### 4.2 `agent_run_steps` — looked fixable the same way as the other 4 missing tables, wasn't
- **Tried**: writing a migration to mirror `agent_run_steps` from Lovable's schema, same pattern as
  `contacts`/`outreach_messages`/`roadmap_progress`/`contact_messages`.
- **Failed because**: its FK targets `agent_runs(id)`, but the self-hosted `agent_runs` table (the
  real, Go/Python-managed durable-run-control table, actively used in production) has primary key
  `run_id`, not `id`, and totally different columns. Two unrelated concepts share one table name.
- **Then tried**: considering a rename to a non-colliding table name (`agent_ui_runs` etc.) so the
  Lovable-schema concept could get its own real self-hosted tables without touching the real one.
- **Failed because**: `applyAgent.ts`'s *write* path goes through `supabase.functions.invoke("apply-agent", ...)`
  — a Supabase Edge Function whose source lives in `supabase/functions/apply-agent/index.ts`. Checked
  `supabase-local/docker-compose.yml`'s own header comment: `"Removes: analytics, vector, imgproxy,
  edge-functions"`. Self-hosted has no edge-function runtime at all, by design. Renaming the table
  would make the *read* path (`listAgentRuns`) stop erroring, but "start a new apply-agent run" would
  still be permanently broken — trading a loud, honest failure for a quiet, misleading one.
- **Result**: left completely untouched. Documented in `lessons.md` and here. This is a real,
  intentional self-hosted-vs-cloud feature gap (`src/pages/ApplyAgent.tsx` genuinely cannot work on
  self-hosted without a Go/Python reimplementation of the edge function), not a bug with a quick fix.

### 4.3 `contact_messages` anon-insert — looked like a real RLS bug, was a curl mistake
- **Tried**: `curl -X POST .../contact_messages` with both `apikey` and `Authorization: Bearer <anon-key>`
  headers set to the same anon key. Got a real `42501 row violates row-level security policy` error.
- **Investigated**: reproduced the identical `INSERT` directly in `psql` as `SET ROLE anon` — it
  **succeeded**. This proved the schema/policy were correct and the failure was HTTP-layer, not SQL.
- **Root cause found**: redundantly passing the anon key as *both* `apikey` and `Authorization: Bearer`
  broke something in Kong/PostgREST's role resolution for this specific case. Dropping the explicit
  `Authorization` header (matching what `supabase-js` actually sends for a genuinely anonymous request)
  gave a real `201 Created`.
- **Lesson**: when a raw HTTP reproduction disagrees with the same operation done directly against
  Postgres as the same role, trust that disagreement as a signal to isolate the HTTP-layer variable
  (headers, in this case) — don't conclude the schema/policy is broken.

### 4.4 First self-hosted-table-parity sweep pass used the wrong ground truth
- **Tried**: checking whether each frontend-queried table name appeared in `backend/db/migrations/*.sql`
  by filename-content grep, to decide what's "missing" from self-hosted.
- **Failed because**: this gave false positives for core, definitely-working tables (`applications`,
  `profiles`, `saved_jobs`) that exist in the self-hosted init bundle under *different* file/migration
  names than their table name would suggest.
- **Fixed by**: checking directly against `CREATE TABLE.*\btable_name\b` in the actual
  `supabase-local/volumes/db/init/*.sql` files — the real ground truth for what's running.

### 4.5 Stale Celery containers silently ran old code with zero error
- **Tried**: after changing `backend/python/app/tasks/automation.py`, rebuilt `go-backend` and
  `python-ai` only, ran the beat task, checked `last_match_count` — it stayed `NULL` with **no
  exception, no warning log, nothing**.
- **Root cause**: `celery-worker`/`celery-beat` are two more separate Docker images built from
  overlapping Python source; they were still running the pre-fix code. Confirmed by `docker exec
  celery-worker python -c "from app.tasks.automation import _count_watch_matches"` → `ImportError`.
- **Fixed by**: `docker compose build celery-worker celery-beat && docker compose up -d --no-deps
  celery-worker celery-beat`. After that, the exact same test produced a real `last_match_count: 18`.
- **Lesson**: "rebuild the backend" in this stack means four separate images (`go-backend`,
  `python-ai`, `celery-worker`, `celery-beat`), not one — and a stale worker fails silently, not loudly.

## 6. What was learned, and the result of each attempt

Consolidating §4's lessons with a few broader ones from the whole session:

- **"Make it adapt to the website" is best read as "find what the website already promises here
  first."** The single highest-value finding this session (the dead `saved_searches.alert_enabled`
  bell) came from checking what already existed before writing anything new, not from the "intelligence"
  features themselves.
- **A grep-based sweep for "frontend queries a table that doesn't exist on self-hosted" is a
  real, repeatable, high-signal audit technique for this specific codebase**, because this project has
  a documented, structural risk (three separate migration locations — `backend/db/migrations/`,
  `supabase-local/volumes/db/init/`, and Lovable-managed `supabase/migrations/` — that don't
  auto-sync, per root `CLAUDE.md`'s own Gotchas section). This sweep found 5 real gaps in one session
  using one method. It generalizes; run it again whenever a new `supabase.from(...)` call is added.
- **Live testing against the real stack catches bug classes that no amount of code review or
  unit testing (even with a correct-looking fake driver) can catch.** Two separate instances this
  session: the uuid/text Postgres operator-resolution bug (invisible to `psql` literals and to fake
  Go-driver tests, only visible with a real typed prepared-statement parameter against real Postgres),
  and the global-logout auth bug (invisible to code review because the code "looked right" — the bug
  was in cross-component *interaction*, not in any single function's logic).
- **When cheap/parallel agents are used for research (the 4 haiku ATS-selector agents from earlier
  this session), verify their output against the actual current file before applying anything** — one
  agent reported a false "missing selector" that already existed, one suggested a `:contains()`
  selector that isn't valid CSS. Cheap agents change the economics of *doing* research, not the
  requirement to check the conclusion.
- **Two "looks broken" situations turned out to be testing artifacts, not real bugs** (§4.3's curl
  header mistake, and the coordinate-scaling red herring in §4.1's attempt 2) — worth remembering
  before spending more time chasing either pattern again in this environment.

- **The two auth modes cannot both be tested from one running frontend build.** `VITE_USE_SELF_HOSTED`
  is a module-level constant baked in at Vite build/dev-server start time
  (`import.meta.env.VITE_USE_SELF_HOSTED`), not something that can be toggled live. Testing a direct-
  Supabase feature (`saved_searches`, `contacts`, etc.) requires starting the dev server with
  `VITE_USE_SELF_HOSTED=false`; testing anything that only goes through the Go gateway works either
  way but is cleanest with the `.env` default (`true`). This session switched between them by killing
  and restarting `bun run dev` with different env overrides — slow, but the only way.
- **The RLS-bypass caveat already documented in root `CLAUDE.md`** ("RLS scope" section) is *not* what
  protects any of the tables touched this session (`contacts`, `outreach_messages`, `roadmap_progress`,
  `contact_messages`, `saved_searches`, `job_watches`'s frontend-facing reads) — those are queried
  directly via `supabase-js`/PostgREST as `anon`/`authenticated`, the one path where RLS *does* apply
  for real. The BYPASSRLS caveat only matters for Go/Python-mediated queries (e.g. `job_watches`'s
  Celery beat task, which connects as `postgres`). Both security models are real and both are in play
  simultaneously in this codebase — don't conflate them when reasoning about a new table's safety.
- **If you rebuild any Python-touching container, rebuild all four**: `go-backend`, `python-ai`,
  `celery-worker`, `celery-beat`. `docker compose build <service>` then `docker compose up -d --no-deps
  <service>` per service (the `--no-deps` avoids an unwanted cascade rebuild/recreate of unrelated
  services like `supabase-db`, which happened once this session by accident — harmless since it just
  restarted, but worth avoiding).
- **`lessons.md` has the full, detailed, dated write-up of every fix this session** (search for
  "2026-08-27" and "2026-08-28" entries) — read those before re-deriving anything summarized here from
  scratch. This handoff is the fast-orientation version; `lessons.md` is the evidence trail.
